# 桌面记忆数量与数据库不一致

历史版本中，记忆管理接口曾默认使用 `default` 用户，而桌面聊天使用
`desktop_user`。修正接口后，留在旧归属下的记忆仍然存在，但不会出现在
桌面列表中；图谱也可能出现相同情况。

## 自动恢复

包含此修复的桌面后端在初始化主记忆库时自动检查归属。必须由桌面应用
启动（有 `OPENAKITA_DESKTOP_SESSION_TOKEN`），并且语义记忆、图谱节点和
会话登记中没有 `default`、`desktop_user` 以外的用户或未知身份，才会自动处理。
检查覆盖所有工作空间；系统及隔离区语义记忆不参与用户判断。

符合条件时，程序会：

1. 创建并校验完整 SQLite 备份，包含已提交的 WAL 数据。
2. 在一个事务内，将默认工作空间下 `default` 用户的用户/会话记忆、
   图谱节点、会话登记改为 `desktop_user`，记录迁移审计。
3. 刷新主记忆管理器缓存，统一默认工作空间中新会话的默认用户身份。

迁移保留记录 ID、正文、时间戳、过期状态、替代关系和图谱连接，不调用
LLM，也不重新审查或去重。因此页面显示的是迁移后的有效记忆数，未必等于
数据库全部行数。其他工作空间、系统记忆、历史隔离区、待整理区保持原样。

备份位于记忆库旁，名称为 `openakita.db.bak.desktop_owner.<时间戳>`。
备份或迁移失败时保持原数据，下一次启动重试。一个进程中共享同一数据库的
后续管理器不会再次迁移；下次启动仍会检测从旧版本新导入的记录。

CLI、独立 API 服务、独立 Agent 记忆库不自动迁移。存在其他用户或未知身份的
数据库会跳过自动处理，需先确认归属，再使用 `/api/memories/merge-owner`
进行预演和人工迁移。这个人工接口只处理有效语义记忆，不迁移图谱和会话。

## 验证

在用户电脑访问 `http://127.0.0.1:18900/api/memories/migration-status`
（自定义端口时替换端口），检查 `current_visible`、`semantic.by_owner` 和
`graph.by_owner`。日志中的 `[Memory] Desktop owner alignment` 会记录迁移数量、
备份位置或跳过原因；迁移异常会记录 `Desktop owner alignment failed`。

这项恢复不适用于普通搜索/类型筛选、记忆过期或抽取失败造成的数量差异。
